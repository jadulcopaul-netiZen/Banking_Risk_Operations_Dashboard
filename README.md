# Banking Risk Operations Dashboard

## Project Overview

This project demonstrates an end-to-end data engineering workflow that ingests raw synthetic banking transaction data, applies evidence-based transformation and rule-based data quality validation through Power Query, logs historical data quality and idempotency metadata using Python, and delivers stakeholder-tiered fraud analytics through Power BI.

## Business Scenario

Fraud operations teams need earlier visibility into fraudulent transaction activity to reduce financial exposure and improve response time. This project simulates a fraud operations use case across three stakeholder tiers — strategic (executives, risk, compliance), tactical (operations managers, fraud investigators), and operational (analysts, contact centers) — translating raw transaction data into tiered KPIs: fraud rate, fraud exposure amount, and transaction volume patterns across simulated time and transaction type.

## System Architecture

### Overview

The pipeline follows a layered medallion architecture:

```
PaySim CSV (Kaggle)
    ↓
Bronze Layer (create_dev_sample.py — reproducible 200K-row sample)
    ↓
Silver Layer (power_query_etl.xlsx — ETL transformation + Data Quality validation)
    ↓
Gold Layer (gold.xlsx — fact_transactions + dim_time, pulls validated data from Silver)
    ↓
Historical Monitoring (log_dq_history.py — DQ history + dataset fingerprinting)
    ↓
Power BI Semantic Model → Fraud Operations Dashboard
```


*High-level data flow. See the layer descriptions below for the full technical breakdown, including the historical monitoring and data quality layers.*

### Description of Layers

- **Bronze:** Raw PaySim data is reduced to a reproducible, deterministic 200,000-row development sample (`random_state=42`), preserving the original dataset's transaction volume patterns and fraud distribution.
- **Silver:** Power Query standardizes data types and derives analytical attributes (`amount_range`, `simulation_day`/`hour`/`time`, balance-change fields) based on profiling findings. A 22-rule Data Quality framework (completeness, validity, uniqueness, consistency) validates this layer.
- **Gold:** Restructures Silver's validated data into a fact/dimension model (`fact_transactions`, `dim_time`) for reporting. Carries forward Silver's DQ results rather than re-validating independently (see Known Limitations).
- **Historical Monitoring:** A Python script logs DQ results and transaction data to append-only history files, using SHA-256 dataset fingerprinting to prevent duplicate logging of unchanged data across repeated runs (idempotency).
- **Power BI:** Consumes the Gold layer only — never reaches back into Silver or raw data — to deliver a 4-page report (Overview, Operations, Risk Analysis, Data Quality) aligned to stakeholder tiers defined in the Business Scenario.

### Design Principle

The system favors the simplest architecture that meets actual requirements over complexity for its own sake. A direct CSV-to-Power-BI connection was explicitly considered as a cheaper alternative for a one-time, small-scale dashboard, but the layered approach was retained to demonstrate reproducibility, reusable prepared data, and separation of data preparation from reporting — explained further in Future Improvements.

## Setup Instructions

This project is designed to run end-to-end from raw data ingestion through dashboard refresh.

### Step 1: Clone the Repository

```bash
git clone https://github.com/jadulcopaul-netiZen/Banking_Risk_Operations_Dashboard.git
cd Banking_Risk_Operations_Dashboard
```

### Step 2: Create and Activate a Virtual Environment

A virtual environment isolates project-specific Python packages from your global Python installation, ensuring consistent and reproducible dependency management.

```bash
python -m venv venv
```

Activate it depending on your terminal:

**PowerShell**
```powershell
.\venv\Scripts\Activate.ps1
```

**Git Bash**
```bash
source venv/Scripts/activate
```

After activation, your terminal should display `(venv)`, indicating the virtual environment is active.

### Step 3: Install Project Dependencies

```bash
pip install -r requirements.txt
```

### Step 4: Download the Dataset

The raw dataset is intentionally excluded from this repository to reduce repository size.

Download from Kaggle: **https://www.kaggle.com/datasets/ealaxi/paysim1** \
Download Via: Kaggle CLI \
Select Download dataset as zip 

Create folder inside data named archive \
Place the zip file at: data/archive \
Extract the data there and you'll have /data/archive/archive/PS_20174392719_1491204439457_log.csv 

After downloading and extracting, confirm the file:
- Filename: `PS_20174392719_1491204439457_log.csv`
- Size: approximately 482 MB

### Step 5: Generate the Bronze Layer

```bash
python scripts/create_dev_sample.py
```

Expected output:

```bash
Sample created successfully.
Rows: 200000
Step range: 1 -> 736
```


### Step 6: Refresh the Silver Layer

Open `data/silver/power_query_etl.xlsx` and refresh the Power Query connection (Data tab → Refresh All).

The Silver layer's source path resolves automatically using a dynamic formula tied to the workbook's own location — no manual path configuration is required, regardless of where the repository is cloned.

Confirm the `dq_all_results` query shows 22 rows (data quality checks).

### Step 7: Refresh the Gold Layer

Open `data/gold/gold.xlsx` and refresh (Data tab → Refresh All).

Like Silver, Gold's source path resolves automatically relative to its own workbook location.

### Step 8: Run Historical Monitoring

```bash
python scripts/log_dq_history.py
```

**Note:** Ensure `data/monitoring/dq_run_history.csv` and `transaction_run_history.csv` are not open in Excel before running — an open file will cause a `PermissionError`.

Expected output includes:

```bash
historical logging completed successfully
dq records logged: 22
total transactions: 200000
```


### Step 9: Refresh the Dashboard

Open `dashboard/banking_risk_operations_dashboard.pbix`.

**Before refreshing**, update the two Power BI parameters to match your local file paths:

1. Home tab → Transform Data → Manage Parameters
2. Update `GoldFilePath` to the full path of your local `data/gold/gold.xlsx`
3. Update `MonitoringCSVPath` to the full path of your local `data/monitoring/transaction_run_history.csv`

Then: Home tab → Refresh.

**Note:** Navigation buttons between report pages require **Ctrl+Click** when viewing inside Power BI Desktop's editing view. They respond to a normal click once published or viewed outside the editor.

### Step 10: Verify

After refresh, confirm the dashboard displays:
- Total Transactions: 200,000
- Fraudulent Transactions: 268
- Fraud Rate: 0.1340%

## Known Limitations

- **Partially manual pipeline:** Python steps (Bronze sampling, historical monitoring) are fully automated, but Silver, Gold, and the Power BI dashboard require manual refresh — there is no single command that runs the entire pipeline end-to-end.
- **Gold-layer data quality is not independently validated:** The 12-rule Data Quality framework (22 check results) runs at the Silver layer only. Gold’s dq_all_results is a copy of Silver’s results, and Gold restructures Silver’s data into fact_transactions and dim_time. No check confirms that every fact row matches a dim_time row or that dim_time keys are unique. This item was deferred in Phase 6 and remains open.
- **Power BI path configuration is manual, not automatic:** Unlike the Excel-based Silver and Gold layers (which resolve their source paths automatically via a dynamic formula), Power BI's data source paths are managed through Parameters that must be manually updated after cloning to a new machine. Power BI does not support the same self-locating technique available in Excel.
- **Synthetic, static, single-sample dataset:** PaySim is synthetic and may not fully represent real banking fraud behavior. The pipeline has been validated against one deterministic 200,000-row sample (`random_state=42`); it has not been tested against a structurally different dataset of the same schema (robustness testing, distinct from the reproducibility testing already completed).
- **No automated environment setup from project start:** A virtual environment was introduced only during Phase 9 reproducibility testing. Earlier development relied on a global Python installation, which is documented here rather than retroactively obscured.

## Future Improvements

- Implement a referential integrity check between `fact_transactions` and `dim_time` at the Gold layer.
- Automate the Python historical-monitoring step to trigger after each Power Query refresh, reducing manual pipeline steps.
- Replace CSV-based historical monitoring with a database-backed store for better query performance and concurrency handling at scale.
- Test pipeline robustness against a structurally varied dataset (same schema, different volume/distribution), separate from the reproducibility testing already completed.
- Migrate from pandas to a distributed processing framework (e.g., PySpark) if the dataset scale exceeds single-machine memory constraints — the original 8GB RAM development constraint that drove the 200K-row sampling decision in Phase 0.
- Introduce incremental loading if the data source becomes continuously updated, rather than the current static full-refresh approach (full refresh was deliberately chosen in Phase 4 due to `step` being an unreliable watermark for a static source).
